# Webhook Events

This document provides a detailed description of each webhook event, including
the event name, trigger condition, a full JSON payload example, and HMAC
verification code samples.

> **Stability note:** All events listed below actually fire in the
> implementation. The enum also defines `account.claimed` and
> `payment.received` for future use but those do not currently fire.

---

## `account.created`

Triggered when an ephemeral account is provisioned and the Soroban
`EphemeralAccount.initialize()` contract call succeeds.

### Payload Example

```json
{
  "id": "evt_a1b2c3d4e5f6",
  "event": "account.created",
  "version": 1,
  "accountId": "acc_01J3Z4Y2eZvKYlo2C0T4Q5R6p",
  "publicKey": "GAXD53RJ7ZCKI5V2ZJQPX7B3XK4Q6S2RZ4YCD5XGELVXQQE3LPXG2AQF",
  "amount": "100.0000000",
  "asset": "USDC:GBBD47IF6LWK7P7MHY3KUX7W2V6WOPARAUI3VLH22XXBHUSA7NINWY4F",
  "expiresAt": "2024-02-01T00:00:00.000Z"
}
```

| Field       | Type                | Description                                          |
| ----------- | ------------------- | ---------------------------------------------------- |
| `id`        | `string`            | Delivery UUID generated by the webhook system        |
| `event`     | `string`            | Always `"account.created"`                           |
| `version`   | `number`            | Payload schema version (see Schema Versioning below) |
| `accountId` | `string`            | Internal account identifier                          |
| `publicKey` | `string`            | Stellar public key of the ephemeral account          |
| `amount`    | `string`            | Amount deposited (decimal string)                    |
| `asset`     | `string`            | Asset code and issuer (`CODE:ISSUER`) or `"native"`  |
| `expiresAt` | `string` (ISO 8601) | When the account expires                             |

## `sweep.completed`

Triggered when a claim redemption completes successfully: the Soroban
`SweepController.execute_sweep()` authorises the sweep **and** the Horizon
classic payment lands.

### Payload Example

```json
{
  "id": "evt_c3d4e5f6g7h8",
  "event": "sweep.completed",
  "version": 1,
  "accountId": "acc_01J3Z4Y2eZvKYlo2C0T4Q5R6p",
  "amount": "100.0000000",
  "asset": "USDC:GBBD47IF6LWK7P7MHY3KUX7W2V6WOPARAUI3VLH22XXBHUSA7NINWY4F",
  "destination": "GDEST47IF6LWK7P7MDEVSCWR7DPUWV3NY3DTQEVFL4NAT4AQH3ZLLFLA",
  "txHash": "a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2",
  "sweptAt": "2024-01-15T12:34:56.789Z",
  "metadata": {
    "orderId": "12345"
  }
}
```

| Field         | Type                | Description                                          |
| ------------- | ------------------- | ---------------------------------------------------- |
| `id`          | `string`            | Delivery UUID                                        |
| `event`       | `string`            | Always `"sweep.completed"`                           |
| `version`     | `number`            | Payload schema version (see Schema Versioning below) |
| `accountId`   | `string`            | Internal account identifier                          |
| `amount`      | `string`            | Amount swept (decimal string)                        |
| `asset`       | `string`            | Asset code and issuer                                |
| `destination` | `string`            | Stellar address that received the funds              |
| `txHash`      | `string`            | Horizon transaction hash of the payment              |
| `sweptAt`     | `string` (ISO 8601) | When the sweep was recorded                          |
| `metadata`    | `object`            | Forwarded from the original account creation request |

## `sweep.partial`

Triggered when the Soroban `SweepController.execute_sweep()` contract
call succeeds (authorisation is on-chain) but the subsequent Horizon
classic payment **fails**. The account is left in `PARTIAL_SWEEP` status
so a retry can re-submit the payment without re-invoking the contract.

### Payload Example

```json
{
  "id": "evt_d4e5f6g7h8i9",
  "event": "sweep.partial",
  "version": 1,
  "accountId": "acc_01J3Z4Y2eZvKYlo2C0T4Q5R6p",
  "amount": "100.0000000",
  "asset": "USDC:GBBD47IF6LWK7P7MHY3KUX7W2V6WOPARAUI3VLH22XXBHUSA7NINWY4F",
  "destination": "GDEST47IF6LWK7P7MDEVSCWR7DPUWV3NY3DTQEVFL4NAT4AQH3ZLLFLA",
  "error": "Horizon connection timeout after 30s",
  "contractAuthHash": "a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2"
}
```

| Field              | Type     | Description                                                         |
| ------------------ | -------- | ------------------------------------------------------------------- |
| `id`               | `string` | Delivery UUID                                                       |
| `event`            | `string` | Always `"sweep.partial"`                                            |
| `version`          | `number` | Payload schema version (see Schema Versioning below)                |
| `accountId`        | `string` | Internal account identifier                                         |
| `amount`           | `string` | Amount intended for sweep                                           |
| `asset`            | `string` | Asset code and issuer                                               |
| `destination`      | `string` | Stellar address that should receive the funds                       |
| `error`            | `string` | Description of the Horizon payment failure                          |
| `contractAuthHash` | `string` | SHA-256 hash of the contract authorisation inputs (for audit trail) |

## `sweep.failed`

Triggered when a claim redemption fails entirely — either the Soroban
contract call fails or an unrecoverable error prevents the sweep from
proceeding.

### Payload Example

```json
{

  "version": 1,

  "destination": "GDEST47IF6LWK7P7MDEVSCWR7DPUWV3NY3DTQEVFL4NAT4AQH3ZLLFLA",
  "error": "Stellar network error: Soroban RPC timeout",
  "timestamp": "2024-01-15T12:34:56.789Z"
}
```

| Field         | Type                | Description                                          |
| ------------- | ------------------- | ---------------------------------------------------- |
| `id`          | `string`            | Delivery UUID                                        |
| `event`       | `string`            | Always `"sweep.failed"`                              |
| `version`     | `number`            | Payload schema version (see Schema Versioning below) |

| `amount`      | `string`            | Amount that failed to sweep                          |

## HMAC Verification

Every outbound webhook includes an `X-Bridgelet-Signature` header
containing a HMAC-SHA256 digest of the raw request body, signed with
the secret configured on the webhook subscription.

### TypeScript

```typescript
import * as crypto from 'crypto';

const secret = 'your-webhook-secret';
const signature = request.headers['x-bridgelet-signature'];
const body = request.rawBody;

const hmac = crypto.createHmac('sha256', secret);
const digest = `sha256=${hmac.update(body).digest('hex')}`;

if (digest !== signature) {
  // Invalid signature — reject the request
}
```

### Python

```python
import hashlib
import hmac

secret = b'your-webhook-secret'
signature = request.headers.get('X-Bridgelet-Signature')
body = request.get_data()

digest = 'sha256=' + hmac.new(secret, body, hashlib.sha256).hexdigest()

if not hmac.compare_digest(digest, signature):
    # Invalid signature — reject the request
```

### Go

```go
import (
	"crypto/hmac"
	"crypto/sha256"
	"encoding/hex"
	"net/http"
)

func verifySignature(r *http.Request, body []byte) bool {
	secret := []byte("your-webhook-secret")
	signature := r.Header.Get("X-Bridgelet-Signature")

	mac := hmac.New(sha256.New, secret)
	mac.Write(body)
	expectedSignature := "sha256=" + hex.EncodeToString(mac.Sum(nil))

	return hmac.Equal([]byte(signature), []byte(expectedSignature))
}
```

## Schema Versioning & Backward Compatibility

Every payload includes a top-level `version` field (currently `1`). It is
set in one place (`WebhookDeliveryProvider.deliver()`) and applied to every
event type, so it is always present regardless of which event fired.

Integrators should read `version` and branch their parsing logic on it
rather than assuming today's documented shape is permanent.

### What counts as a breaking change (requires a version bump)

- Removing a field
- Renaming a field
- Changing a field's type (e.g. `amount` changing from a decimal string to
  a number)
- Changing the semantic meaning of an existing field's value

### What does not require a version bump

- Adding a new, optional field to an existing event's payload
- Adding an entirely new event type
- Fixing a bug where a field's value was incorrect but its type and meaning
  were unchanged

### Policy

- A version bump is announced in the changelog and, where practical, via
  advance notice to registered webhook subscribers before the new version
  starts being sent.
- The previous version's documented shape remains supported for a
  deprecation window communicated at bump time — integrators are not cut
  over without warning.
- `docs/webhook-events.md` is kept in sync with whatever version is
  currently live; it documents actual behaviour, not aspirational schema.
